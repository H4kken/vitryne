# WebGPU Garment Drape Spike — Report

> **Archive.** This is the `drape-spike` report as it stood at the end of the spikes (2026-10-12), kept for its history and numbers. Paths in it are the spike's: the analysis scripts now live in `tools/bench/`, and the raw benchmark output (`bench/…`) was left out of this repository's history to keep it small. Current progress is in [../../PROGRESS.md](../../PROGRESS.md).

**Question:** can garment-grade cloth simulation run in the browser on WebGPU at usable speed, from one Rust + wgpu codebase that also runs natively?

**Short answer:**
- **The browser isn't the limiting factor.** On an Apple M2, the same engine runs in Chrome and Safari at 1.02–1.19× native cost, with the same results.
- **The core user-facing tests pass in both browsers:** the drape to rest, interactive drag and body penetration.
- **The stability test fails on its raw speed limit, and self-collision falls short in pinched regions, natively too.** Both are solver-quality problems, not browser problems: a server running the same engine would fail the same way.
- **Untested:** Firefox and the Windows laptop. Safari wasn't rerun for M5, and its numbers below come from M3/M4.

**Setup:**
- **Machine:** MacBook Air, Apple M2 (integrated GPU), macOS.
- **Browsers:** Chrome 150 (headless, real GPU) and Safari 27.0.1.
- **Stack:** Rust 1.99, wgpu 30.0.1. `Features::empty()` and `Limits::default()` on every target; WebGPU backend only in wasm; one set of WGSL shaders.
- **Simulation:** 20 substeps × 1 iteration XPBD, at 60 Hz frames.
- **Data:**
  - Raw JSON: `bench/m5/` (this report), plus `bench/m3/` and `bench/m4/` for Safari.
  - Tables: generated by [bench/m5/tables.py](../../tools/bench/m5/tables.py).
  - Method and history: [PROGRESS.md](PROGRESS.md).

**Notes on the criteria:**
- **Speed limit:**
  - Each violation lasts 1–7 frames out of 3,600 (≤ 0.2% of the time), then the cloth recovers at once.
  - With gentle drags (5–15 cm over ≥ 0.5 s), self-collision off: 1 frame in 3 runs, in both native and Chrome.
  - The same seeds spike natively. The cause is contact in narrow body creases (armpit, between the thighs) and free edges whipped by hard pulls; see "Bottlenecks and weak spots".
- **Self-collision:**
  - It removes every intersection in the folding test (dropped sheet: 91 → 0 persistent) and never leaves one in the drape.
  - It cuts drag-test damage from 80–121 pairs to 11–30.
  - It fails only where the sleeve is pinched between arm and torso and pushed through itself. Point-to-point repulsion can't untangle a crossing once it exists.
- **Tolerance:**
  - Drape: identical rest frames on every target, and a final shape within 0.11 mm per vertex (≤ 0.37 mm in Safari with SC).
  - Drags: the same spike counts per seed within ±1 frame.
  - Long chaotic drag sequences diverge after a few dozen episodes: seed 5's final state differs between native and Chrome even without SC. Each target is bit-reproducible run to run.

## Decision

**Decision rule, applied literally:**
- **"All core tests pass in ≥ 2 browsers"** → **not met.** The raw stability limit (< 5 m/s) fails in Chrome and in Safari. Only 2 browsers were measured, and Safari's M5 rerun was skipped.
- **"Drape passes, self-collision fails"** → **this is the matching branch:** the browser for single-layer preview, the server for full simulations.

**What the numbers actually say:**
1. **The browser runs the solver at native speed:** 1.02–1.19× native, 1.5–1.7 µs per dispatch vs 1.45 µs natively, and identical drapes.
2. **Every failing test fails identically natively.** Moving the simulation to server GPUs with the same engine wouldn't fix the speed spikes or the pinched-armpit intersections; it would only add latency.
3. **The failures are solver work:** crease-aware body contact and an untangling pass for self-collision. That work is needed wherever the solver runs.

**Recommendation:**
- **Treat client-side simulation as viable for single-layer garments on Apple Silicon.** The drape, the interaction and the penetration targets hold with a large margin: rest in < 1.2 s at 20k vertices with self-collision, and 55+ fps while dragging.
- **Make two things preconditions, not open questions:**
  - **(a) Confirm on Windows + Firefox.** Open `bench.html`, press Run, Copy JSON. There's no Apple-specific code, but the integrated-GPU Windows laptop is the realistic low end and hasn't been measured.
  - **(b) Fix the crease contact.** It produces both the speed spikes and the persistent intersections, and it's the same fix for client and server.
- **Keep the native build** as the server/offline path for multi-layer or very high-resolution simulations. It's the same code.

## Bottlenecks: what dominates GPU time

Profiling mode: `timestamp-query`, one pass per phase per substep, in ms per frame. The absolute numbers include per-pass overhead; the shares are what matter.

| | Vertices | Bend | Stretch + sew | Body collide | Self-coll: hash rebuild + query | Self-coll: per-substep collide | Rest | Top phase |
|---|---|---|---|---|---|---|---|---|
| Native, SC off | 10k | 1.00 | 0.64 | 0.32 | — | — | 0.22 | **bend 46%** |
| Native, SC off | 40k | 2.94 | 1.69 | 0.78 | — | — | 0.64 | **bend 49%** |
| Chrome, SC off | 10k | 1.21 | 0.68 | 0.31 | — | — | 0.19 | **bend 51%** |
| Chrome, SC off | 40k | 3.38 | 1.41 | 0.67 | — | — | 0.38 | **bend 58%** |
| Native, SC on | 10k | 1.17 | 0.75 | 0.47 | 0.66 | 0.38 | 0.23 | bend 32%, self-coll 29% |
| Native, SC on | 40k | 3.00 | 1.72 | 0.80 | 1.62 | 1.41 | 0.76 | bend 32%, self-coll 33% |
| Chrome, SC on | 10k | 1.62 | 0.90 | 0.52 | 0.77 | 0.37 | 0.23 | bend 37%, self-coll 26% |
| Chrome, SC on | 40k | 3.41 | 1.50 | 0.77 | 1.34 | 1.26 | 0.50 | bend 39%, self-coll 30% |

1. **Bending is the largest single phase everywhere:** 45–58% of the time with SC off. It has 18 graph colours, so 18 dispatches per substep.
2. **Dispatch count is the hidden fixed cost.**
   - **Per frame:** 640–660 dispatches at 10–40k vertices with SC off, 705–725 with SC on (20 substeps).
   - **Per dispatch:** 1.45 µs natively, 1.5–1.7 µs in the browsers.
   - **Share at 10k:** about 1 ms of the 1.8 ms frame is overhead, which is why cost grows sub-linearly with vertex count.
   - **Levers:** fewer colours, merging the stretch and bend passes, or fewer substeps with more iterations.
3. **Self-collision costs:**
   - **Hash build (counting sort):** cheap, about 30 µs.
   - **Neighbour query:** the expensive part. It's latency-bound, because each thread runs a chain of dependent reads.
   - **Rebuilding every substep** (the plan's literal version) doubles the frame cost; **every 4th** costs +45–65% with the same quality.
4. **Memory:** the largest buffer is the 4 mm body SDF, 50.2 MB, under the 128 MiB binding limit. Everything else is < 10 MB at 40k.
   - **Delivery:** the SDF is a 15 MB gzip download.
   - **Baking it in wasm instead** takes 9.3 s single-threaded, so it should be downloaded or baked on a server.

**Weak spots that cause the failures (all identical natively):**
- **Body creases:**
  - **Mechanism:** a per-vertex SDF contact can't represent a gap narrower than 2 × the 2 mm contact thickness, plus the self-collision radius.
  - **Where:** the armpit in A-pose, and between the thighs for a dragged hem.
  - **Effect:** cloth pinched there gets pushed through itself, which leaves persistent intersections, or snaps out, which gives the speed spikes.
  - **Options:** triangle-level body contact, a velocity filter at contacts, or a wider arm–torso gap in the avatar pose.
- **Untangling:** point-to-point repulsion can't tell which side a layer belongs on, so a crossing that already exists stays.
  - **Options:** intersection-contour untangling (Baraff et al. 2003; Volino & Magnenat-Thalmann 2006) or continuous triangle collision.
- **Whipping free edges under hard pulls:** mitigated with XPBD damping and air drag, but not removed.

## Browser-specific findings and bugs

| What | Where | Impact / workaround |
|---|---|---|
| No WebGPU adapter in gstack's headless Chromium | tooling | Automation drives the installed Chrome over CDP (`web/tools/chrome-check.mjs`) with the GPU on. `--virtual-time-budget` breaks async GPU init. |
| Chrome hides the adapter name and vendor (empty strings, type `Other`) | Chrome | The machine has to be recorded by hand in reports. |
| Fine-grained `performance.now()` needs cross-origin isolation | all browsers | COOP/COEP headers on the dev server. |
| Safari can't be automated without a sudo setting | Safari | Pages run from `?auto=1` and POST their JSON to a dev-only endpoint. |
| Safari: stale tabs reloaded by Vite HMR competed for the GPU and stalled runs | Safari | Close test tabs and don't edit `web/` during runs. |
| Safari: the long drag benchmark runs much slower (about 3 min per seed vs 25 s in Chrome); one tab disappeared mid-run | Safari | Likely the per-frame metrics readback latency, which only the benchmark does; the interactive viewer runs at 55+ fps. Not investigated. The SC drag test isn't measured in Safari. |
| Shader compilers differ (Tint, WebKit's compiler, naga → MSL) | all targets | Results aren't bit-identical, but they match within 0.11–0.37 mm for the drape. Long chaotic drag runs diverge. |
| Canvas uses a non-sRGB format, so the shading is darker than native | all browsers | Cosmetic; rendering is out of scope. |
| Browser `timestamp-query` works (core WebGPU, pass-level writes) | Chrome, Safari | Profiling works in the browser without native-only features. |

**No WebGPU correctness bug was found** in Chrome or Safari: no validation errors, no limit problems, and no wrong results. Every number above uses the default limits, with 7–8 storage buffers per stage at most.
